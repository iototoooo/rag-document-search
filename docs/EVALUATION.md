# 精度検証 — 方法と結果記録

テスト質問 CSV（該当あり + 文書に記載のない質問）で、正答率・検索ヒット率・出典の正確性・応答時間を測定します。

> **結果の要約（2026-11-23・実 API 1 回）**
>
> - 正答率 **100%（12/12）**、文書に記載のない 2 問も 2/2 で捏造なし。
> - これは**学習用の配布資料（ダミーの社内文書 5 件・テスト質問 12 問）での実測結果**です。配布資料は再配布できないため、このリポジトリには含めていません。
>   **本リポジトリの架空のテストデータや、ほかの文書で同じ結果になることを保証するものではありません。**
> - 応答時間は p50 2.0 秒ですが、1 問が 7.7 秒かかり、**目標の p95 5 秒以内は未達**です（12 問のため p95 = 最大値）。
> - 測定は 1 回・12 問のみで、インメモリ索引（DB・Vercel の遅延を含まない）での結果です。

## 1. 目標

| 指標 | 目標 | 判定方法 |
| --- | --- | --- |
| 正答率 | **80% 以上** | 実 API モードの「正答」列 |
| 文書に記載のない質問 | すべて「該当する情報が見つかりません」 | 実 API モードの「該当なし質問の正答」 |
| 応答時間 | **p95 で 5 秒以内** | 実 API モードの応答時間（Embedding + 検索 + 回答生成） |

## 2. 指標の定義

| 指標 | 定義 |
| --- | --- |
| 正答（該当あり） | `found = true`、かつ期待回答の**要点**（数値＋単位・時刻）をすべて含み、かつ期待文書の出典が 1 つ以上ある |
| 正答（該当なし） | `found = false`、かつ出典が 0 件 |
| 要点 | CSV の「期待される回答」から自動抽出（例: `1泊12,000円まで` → `12000円`、`11:00〜15:00` → `11:00`/`11時`・`15:00`/`15時`）。桁区切り・全角・「か月」等の表記ゆれは吸収 |
| 検索ヒット率 | 該当ありの質問のうち、期待文書のチャンクが検索上位（`RAG_MATCH_COUNT` 件）に入った割合 |
| 出典の正確性 | 返された出典のうち、期待文書のものの割合（平均） |
| セクション一致 | 出典の見出しが CSV の「出典セクション」と一致したか（参考値） |
| 応答時間 | 1 問ごとの Embedding + 検索 + 回答生成の時間（インメモリ索引のため DB・Vercel の遅延は含まない） |

自動判定は要点の文字列一致による**機械的な判定**です。言い換えで不正解になる場合があるため、実 API の結果は必ず人が回答本文を確認し、判定を修正した場合は理由を記録してください。

## 3. 実行方法

文書と質問 CSV は各自で用意します（[README](../README.md)「文書・テストデータについて」）。

```powershell
# モック（外部通信なし・無料）: 検索ヒット率と配線の確認
npm run eval
npm run eval -- --pdf-dir <PDF のフォルダ> --csv <質問 CSV>

# ⚠ 実 API（OpenAI + Claude・課金あり。目安: 12 問で $0.2〜0.4）
npm run eval -- --live --execute
npm run eval -- --live --execute --only 11,12   # 指定した質問だけを検証
```

- 結果は `reports/eval/<日時>-<mock|live>.md` と `.json` に保存（`.gitignore` 対象。回答・抜粋を含むため公開しない）。
- 実 API モードでも **DB（Supabase）は使わず**、PDF をメモリ上に取り込んで評価します。DB・RLS を含む確認は画面からの手動確認と `npm run verify:db` で行います。
- `--live` だけでは実行されません（`--execute` の明示が必要）。
- CSV の期待回答に「12,000円」のようなクォートされていないカンマがあっても、前 2 列・後 3 列が固定であることを利用して読み込み時に復元します（`src/lib/documents/csv.ts`）。

自動テスト（`src/lib/eval/eval.test.ts`）では、架空の文書 3 件・質問 7 問（`tests/fixtures/demo-corpus.ts`）で、CSV の読み込み・要点抽出・採点・集計を外部通信なしで検証しています。

## 4. 結果記録

### 4-1. モック（2026-11-22・外部通信なし・学習用の配布資料）

| 項目 | 結果 |
| --- | --- |
| 条件 | モック Embedding（文字 bigram）・モック回答生成、しきい値 0、文書 5 件 / チャンク 14 件 |
| 検索ヒット率 | 上位 6 件・3 件・1 件とも **100%**（10/10） |
| 正答率・応答時間・該当なし質問 | **測定対象外**（モックのため） |

配線と採点ロジックの確認であり、**実 Embedding・実 LLM での精度を示すものではありません。**

### 4-2. 実 API（2026-11-23・学習用の配布資料）

| モデル / effort | 検索設定（しきい値 / 件数） | 正答率 | 検索ヒット率 | 出典正確性 | 該当なし | 応答時間 p50 / p95 / 最大 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| claude-opus-5-5 / low（fallback off） | 0.3 / 6 | **100%（12/12）** | 100%（10/10） | 100%（文書単位）・セクション一致 10/10 | **2/2** | 2,049 / 7,719 / 7,719 ms（平均 2,548 ms） | 正答率: **達成** / 応答時間: **未達** |

- 実行条件: 12 問を 1 回のみ。再試行 0 回・出力上限 3,000 トークンで実行。エラー 0 件。
- 費用（推定）: Claude 約 $0.2〜0.4、Embedding $0.001 未満。実額は各社の Usage 画面で確認。
- 人による確認: 回答本文の全文を文書と照合し、**自動判定の修正はなし**。文書にない事実の追加は見つからなかった。
- ハルシネーション検証: 記載なしの 2 問では、しきい値 0.3 を超えるチャンクが回答生成に渡されたが、Claude が根拠なしと判断し、推測の回答や出典の付与はなかった。
  つまり「該当なし」の判定は**検索のしきい値ではなくプロンプトとモデルの判断に依存**している（改善案 E-3）。

質問文・期待回答・回答本文は配布資料の内容を含むため、公開リポジトリには記載していません。

## 5. 応答時間の未達について

| 実施日 | 事象 | 原因 | 再検証 |
| --- | --- | --- | --- |
| 2026-11-23 | 12 問中 1 問の応答時間が 7.7 秒（他の 11 問は 1.7〜2.7 秒）で、p95 5 秒以内が**未達** | **未特定**。その質問は検索結果が 1 文書のみで入力が小さく、再試行も 0 回だった。API 側の一時的な遅延、またはモデルの思考量のばらつきの可能性があるが、当時は処理段階ごとの時間を記録しておらず判別できない | 未実施 |

実施した改善（API 呼び出しなし・回答内容に影響しない）:

1. **応答時間の内訳とトークン数の記録**: 評価 CLI の結果に、質問ごとの Embedding / 検索 / 回答生成の時間と Claude の入力・出力トークン数・推定費用を追加。本番の `/api/chat` も同じ値を `[metric:api_chat]` として 1 行ログに出す（数値と短い識別子のみ。質問・資料・回答は出さない）。
2. **API クライアントの再利用**: `/api/chat` で OpenAI・Anthropic のクライアントをリクエストごとに作り直さず、サーバープロセス内で再利用（効果は未測定）。
3. Vercel の関数リージョンを東京（`hnd1`）に指定（Supabase 東京との往復を短くする。効果は未測定）。

## 6. 改善案

| # | 項目 | 内容 | 優先度 |
| --- | --- | --- | --- |
| E-1 | 応答時間の再測定 | 段階別の計測を付けて 2〜3 回測定し、遅延が再現するかを確認。超過が続く場合は画面のストリーミング表示を検討 | 高 |
| E-2 | 費用の実測 | 各回答の `usage` を集計した値で費用を評価する（実装済み・未実測） | 中 |
| E-3 | 該当なし判定の多重化 | 文書と近い話題の記載なし質問を増やして評価し、必要なら `RAG_MATCH_THRESHOLD` を調整 | 中 |
| E-4 | 出典の重複整理 | 同一文書の隣接チャンクが別出典として表示されることがある。同一ファイル・同一ページ範囲の出典をまとめる | 低 |
| E-5 | セクション表示の粒度 | 出典のセクション名が複数見出しの連結になることがある。見出し単位のチャンク分割で具体的にする | 低 |
| E-6 | 評価規模 | 12 問は小さい。文書 200 件規模の運用前に、質問数・言い換え質問を増やした評価セットを作る | Phase 2 |

| 症状 | 考えられる原因 | 改善策 |
| --- | --- | --- |
| 検索ヒットしない | しきい値が高い / 質問と文書の語彙の差 | `RAG_MATCH_THRESHOLD` を下げる、`RAG_MATCH_COUNT` を増やす |
| 検索はヒットするが要点不足 | チャンク境界で要点が分断 / 回答が要約しすぎ | チャンクの重なりを増やす、プロンプトで「数値は資料の表記どおり」を強調 |
| 該当なし質問に回答してしまう | 類似した別の記述を根拠にしてしまう | プロンプトの「根拠がない場合は found=false」を強調、しきい値を上げる |
| 応答時間が 5 秒超 | effort・出力量・資料数・リージョン | effort を `low`、資料数を減らす、Vercel 関数を Tokyo に、必要ならモデル変更 |
