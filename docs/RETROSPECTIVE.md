対象: 案件3 社内文書検索AI（RAG）Phase 1 — 実装・実環境検証・本番デプロイまで（2026-11-22〜2026-11-24）

## Keep（続けたいこと）

- **共通仕様を先に main で確定してから並列実装した。** 型・API 契約・DB スキーマ・担当ファイル表を先に決めたことで、Worktree 3 本の並列実装でもマージ競合ゼロで統合できた。
- **外部サービスを境界インターフェースで分離し、すべてモックでテストした。** 実キー・実 DB なしで 200 件近いテストを回せ、課金・データ送信なしで品質を確認できた。
- **セキュリティを DB 側（RLS）で担保した。** アプリの認可に加えて RLS・security invoker の検索関数・非公開 Storage を組み合わせ、アプリのバグがあっても漏えいしにくい設計にした。マイグレーションも静的テストで常時検査している。
- **「できていないこと」を明記した。** モックと実 API の結果を分けて記録し、精度目標は実環境で確認するまで「達成」と書かない運用にした。

## Problem（課題）

- **PDF 由来の文字の問題**: 抽出テキストに康熙部首（⽇ など）や部首補助文字（⻑ など）が混入し、そのままでは検索で一致しなかった。学習用の PDF を実際に読んで初めて分かった。
- **質問 CSV の形式不備**: 金額のカンマがクォートされておらず列がずれていた。早い段階で列数の厳密なチェックをしていれば初回で気づけた。
- **フレームワークの新仕様**: Next.js 16（Proxy・Cache Components）の挙動が従来と異なり、ビルド時に認可エラー画面が静的に焼き込まれる問題が発生した（修正済み）。
- **シェル・型の細かな失敗**: Windows 環境でのヒアドキュメントの解釈失敗、Supabase クライアント型の展開エラー（TS2589）で手戻りがあった。
- **課金設定の初期値が大きかった**: 当初は自動フォールバック有効・再試行 2 回・出力上限 16000 で、費用の上限が読みにくかった（見直し済み）。
- **応答時間の目標が未達**: 12 問中 1 問が 7.7 秒かかり、5 秒以内を満たせなかった。最初の計測で段階別の時間を記録しておらず、原因を特定できていない。

## Try（次に試すこと）

- 段階別の計測（Embedding・検索・回答生成）を付けて応答時間を 2〜3 回再測定し、遅延が再現するかを確認する（EVALUATION.md E-1）。
- 実 DB で `department` 文書を使った権限テストを行い、部署別アクセス制御を有効化する前に漏えいがないことを確認する（Phase 2）。
- 受け取ったデータは取り込み前に「形式チェック」（列数・文字種・抽出結果の目視）を必ず行う。
- Firewall のレート制限を超えたときの動作を確認する。ユーザー単位の正確な制限（共有ストア）も検討する。
- Phase 2 の優先順位（部署別アクセス制御 → 差分更新 → 管理画面）を依頼者と合意する。

## 学んだこと

- RAG の品質は「検索で正しい根拠を拾えるか」と「根拠がないときに答えないか」で決まる。出典 ID をサーバー側で管理すると、存在しない出典を防げる。
- 権限制御は「アプリで守る」だけでなく「DB で守る」設計にすると、レビュー・テストの観点が明確になる。
- AI に並列で作業させるときは、担当範囲と共通契約を文書化して渡すことが最も効果的だった。

### RAG の精度改善で工夫した点

- **テキストの正規化**: NFKC に加えて部首の文字を通常の漢字に変換し、PDF の表記ゆれで検索が外れないようにした。
- **チャンク分割**: 見出し・段落を考慮して分割し、出典のセクション名を保持した。
- **検索のしきい値と件数**: 類似度のしきい値（0.3）と件数（6 件）を設定値にし、根拠の弱いチャンクを回答に使わないようにした。
- **根拠がないときに答えない**: 回答生成に「根拠がなければ該当なし」と判断させる構造化出力を使い、出典番号はサーバー側で検証して存在しない出典を返さないようにした。
- **評価の自動化と人の確認**: 期待回答から要点（数値・時刻）を自動抽出して採点し、実 API の結果は人が回答本文を確認した。質問 CSV の列ずれも読み込み時に補正した。

### 次の案件に活かせる学び

- 応答時間は**最初の計測から段階別に記録**する。後から原因を調べられない。
- ホスティングの**プランの制限（レート制限ルールの件数など）を設計段階で確認**する。公開直前に分かると対策の選択肢が狭くなる。
- パスワード再設定などの**アカウント回復の手段を最初に決めておく**。画面がない場合の管理者手順も用意する。
- 公開する可能性があるなら、**テストデータは最初から架空のものにする**。後から公開用リポジトリを作り直す手間が減る。
- 新しい DB を使うときは、**権限（GRANT）の確認を確認 SQL に含める**。
